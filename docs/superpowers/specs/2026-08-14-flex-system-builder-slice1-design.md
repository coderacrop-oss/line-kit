## 1. เป้าหมาย

สร้างฐานของ Flex System Builder ให้ **ตั้งค่ากิจกรรมบน LINE ได้จากหน้าจอ โดยไม่ต้อง deploy**

สไลซ์นี้คือ **P0 (ฐานราก) + P1 (ตอบกลับอัตโนมัติ · ทักทายเพื่อนใหม่ · การ์ดเมสเสจ · เครื่องยนต์ตัดสินผล)**

### เกณฑ์ว่าสำเร็จ

| # | ตรวจอะไร | พิสูจน์อะไร |
|---|---|---|
| 1 | พิมพ์คีย์เวิร์ดในแชท → ได้การ์ดที่ตั้งไว้ในหน้าจอ | ท่อครบวงจร |
| 2 | แอดเป็นเพื่อน → ได้การ์ดต้อนรับ | `activity.trigger = 'follow'` ทำงาน |
| 3 | กดปุ่มสุ่มรางวัล → ได้รางวัล · กดซ้ำได้ผลเดิม ไม่ได้ซ้ำ | idempotency (BR-32) |
| 4 | ยิง 50 คำขอพร้อมกันบนรางวัลโควตา 10 → ออกพอดี 10 ใบ | ไม่แจกเกินโควตา |
| 5 | **แก้ข้อความการ์ดในหน้าจอ → เห็นผลในแชทเลย** | **คุณค่าทั้งโปรเจกต์** |
| 6 | ลายเซ็นผิด → 401 | ความปลอดภัยของ webhook |
| 7 | `event_log` มี `duration_ms` ทุกแถว | วัด P95 ได้ (§7 · OI-03) |
| 8 | สคริปต์เทียบ schema กับเอกสารผ่าน | schema ไม่แยกทางกับเอกสาร |
| 9 | เทสต์ทั้งหมดเขียว · ชั้น unit รันไม่ต้องต่อเน็ต | แก้โค้ดแล้วรู้ว่าอะไรพัง |

ข้อ 5 คือข้อที่พิสูจน์คุณค่า อีกแปดข้อคือความถูกต้อง

## 2. ขอบเขต

### อยู่ในสไลซ์นี้

- ตอบกลับอัตโนมัติจากคีย์เวิร์ด (`keyword_rule`)
- ข้อความทักทายเพื่อนใหม่ (`activity.trigger = 'follow'`)
- การ์ดเมสเสจ — `flex_bubble` · `flex_carousel` · `text`
- เครื่องยนต์ — เงื่อนไขเข้าเล่น · `resolve` แบบ `fixed` · `weighted` · `quota` · `score` · effects ทั้งสามชนิด
  (`lookup` ไม่อยู่ในสไลซ์นี้ — ต้องมีตารางเทียบซึ่งยังไม่มีเคสใช้)
- โควตารางวัลและสิทธิ์ · ค่าสะสมและจุดปลดล็อก
- หน้าจอหลังบ้าน 15 หน้า
- ส่งขึ้น/ถอน (publish/unpublish) เฉพาะส่วนที่ไม่เกี่ยวกับริชเมนู

### ไม่อยู่ และไม่แกล้งว่ามี

| เรื่อง | ไปไหน | เพราะอะไร |
|---|---|---|
| ริชเมนู · alias · สลับแท็บ | P2 | คนละชุด API ไม่ปนกับข้อความ |
| ริชเมสเสจ · ริชวิดีโอ | P3 | **ติด OI-27** — ตัววาดภาพจากบล็อกยังไม่มีต้นแบบ |
| บล็อกชนิดแถวสถานะ · ช่องแสตมป์ | ภายหลัง | ต้องต่อกับ `stamp_card` |
| ควิซหลายชั้น (MBTI) · คูปอง · บัตรสะสม | ภายหลัง | ต่อยอดจากของในสไลซ์นี้ได้ |
| รายงาน (M10) · PDPA (M12) · API key (M11) | ภายหลัง | 8 จาก 25 จอยังไม่มี spec — ดู §12 |
| ปุ่มลัดใต้ช่องพิมพ์ | OI-28 | ยังไม่ตัดสิน |

## 3. สถาปัตยกรรม

### 3.1 หลักการเดียวที่ต้องจำ

> **`lib/engine/` และ `lib/render/` ห้ามมี import ที่แตะเน็ตหรือฐานข้อมูล**

เหตุผลไม่ใช่ความสวยงาม แต่เป็นสองข้อที่วัดได้

1. **BR-91** บังคับว่า M3 คืนผลลัพธ์กลาง แล้ว M4 กับหน้าตัวอย่างต้องเรียกตัวเดียวกัน — ถ้า renderer บริสุทธิ์ หน้าตัวอย่างเสียบได้โดยไม่ต้องมี LINE และไม่ต้องมี DB
2. **AC-01** วัดด้วยส่วนต่างของโค้ดหลักเท่ากับศูนย์ — ตรรกะที่ปนกับ I/O วัดไม่ได้

### 3.2 โครงโมดูล

```
lib/
  engine/
    entry.ts       เงื่อนไขเข้าเล่น → ผ่าน หรือ ไม่ผ่านเพราะข้อไหน
    resolve.ts     fixed · weighted · quota · score → รายการผลลัพธ์เรียงตามลำดับความชอบ
    effects.ts     ผลลัพธ์ → รายการ effect ที่จะลง (ยังไม่เขียนอะไร)
    decide.ts      ประกอบสามอันบนเป็นผลตัดสินเดียว
  render/
    groups.ts      card_block[] + PlayerState → { top, content, footer }
    flex.ts        สามกลุ่ม → Flex bubble / carousel
    text.ts        สามกลุ่ม → ข้อความล้วน
    vars.ts        แทนค่าตัวแปร {{counter.food}} จาก PlayerState
  match/
    keyword.ts     ข้อความ → keyword_rule (normalize ก่อนจับคู่ · BR-48)
    postback.ts    เข้ารหัส/ถอดรหัส payload · เพดาน 300 ตัวอักษร (BR-33)
  daykey.ts        คำนวณ period_key จาก timezone + day_length ของแคมเปญ
  line/
    verify.ts      ตรวจ x-line-signature            ← เก็บของเดิม
    client.ts      Reply API + timeout               ← เก็บของเดิม ขยาย
    types.ts       ชนิดข้อมูลของ LINE
  db/
    queries.ts     อ่าน config และสถานะ
    apply.ts       เรียก RPC ที่เขียนแบบ atomic
    cache.ts       แคช config ตาม config_version.id

app/
  api/line/webhook/route.ts     ทางเข้าจาก LINE · บางที่สุด
  api/…                         REST ของหน้าจอหลังบ้าน
  (admin)/…                     15 หน้า

supabase/
  migrations/                   SQL ทั้งหมด
  functions/                    SQL function ที่ใช้เป็น RPC

scripts/
  probe-line-limits.mjs         ← เก็บของเดิม · OI-03 ยังต้องวัด
  check-schema-vs-doc.mjs       เทียบ schema กับ L2 §5.2
```

### 3.3 บังคับเส้นแบ่งด้วยเทสต์ ไม่ใช่ด้วยความตั้งใจ

มีเทสต์หนึ่งตัวไล่อ่านคำสั่ง import ของทุกไฟล์ใน `engine/` และ `render/`
เจอ `db/` · `line/client` · `next/` · `fetch` เมื่อไหร่ เทสต์แดงทันที

ไม่มีตัวนี้ เส้นแบ่งจะหลุดในเดือนที่สองเสมอ และหลุดแบบไม่มีใครสังเกต

## 4. Schema

### 4.1 สร้างครบ 37 ตารางใน migration แรก

ตาม DEV-1 ของแผนพัฒนา — เพิ่มตารางทีหลังง่าย แต่แก้ตารางที่มีข้อมูลแล้วยาก

เดิมน่าจะสร้างเฉพาะที่ใช้ **แต่พอสไลซ์นี้รวมการสุ่มรางวัลจริง มันลากตารางฝั่งสถานะมาเกือบหมดอยู่แล้ว** เหตุผลจึงกลับด้าน

| กลุ่ม | ตาราง | ใช้จริงในสไลซ์นี้ |
|---|---|---|
| CONFIG | 23 | 14 |
| CONNECTION | 3 | 3 |
| STATE | 8 | 6 |
| LOG | 5 | 2 |
| SYSTEM | 2 | 2 |

### 4.2 constraint ลงครบตาม §5.5 ตั้งแต่ migration แรก

ตารางตรวจย้อนกลับใน L2 §5.5 มี 81 แถว · ข้อที่บังคับได้ที่ระดับฐานข้อมูลต้องบังคับที่นั่น

สามข้อที่พลาดง่ายที่สุดเพราะเป็น partial unique

```sql
CREATE UNIQUE INDEX ON rich_menu (campaign_id) WHERE is_entry = true;        -- BR-78
CREATE UNIQUE INDEX ON activity  (campaign_id) WHERE trigger = 'follow';     -- BR-90
CREATE UNIQUE INDEX ON channel   (line_channel_id);          -- BR-68 · เต็ม ไม่ใช่ partial
```

ข้อที่สามเคยเขียนผิดในเอกสารว่าเป็น partial · แก้ครบแล้วที่ L2 v0.31

CHECK ที่ห้ามลืมอีกหนึ่งข้อ

```sql
ALTER TABLE card_block ADD CHECK (NOT (content IS NOT NULL AND selector_id IS NOT NULL));
```

ปล่อยให้มีทั้งคู่แล้วจะไม่มีใครรู้ว่าอันไหนชนะ

### 4.3 สคริปต์เทียบ schema กับเอกสาร

การถอด 37 ตารางออกจากเอกสาร HTML ขนาด 329 KB มาลงเป็น SQL ด้วยมือ **คือจุดที่ผิดง่ายที่สุดในสไลซ์นี้**

`scripts/check-schema-vs-doc.mjs` ดึงชื่อตารางกับชื่อคอลัมน์จาก L2 §5.2 แล้วเทียบกับ
`information_schema` ของฐานข้อมูลจริง · **ขาดหรือเกินแม้แต่ช่องเดียวต้องฟ้อง**

สคริปต์นี้อยู่ในชุดเทสต์ถาวร ไม่ใช่ใช้ครั้งเดียวทิ้ง — เอกสารจะเดินต่อไปอีก และวันที่
schema กับเอกสารแยกทางกันคือวันที่เอกสารเริ่มโกหก

## 5. ทางเดินของ event

### 5.1 กิ่งขาเข้า

```
POST /api/line/webhook
  ตรวจลายเซ็น ─── ผิด → 401 จบ ไม่ต้องอ่าน body ต่อ
  ตอบ 200 ให้ LINE ทันที ← ก่อนประมวลผล
  │
  ├── postback ที่มี params.status ──► สลับแท็บ · บันทึก · ไม่ตอบข้อความ   BR-94
  │                                    ต้องแยกก่อนอ่าน payload
  │                                    เพราะไม่มี c= a= d= แนบมา
  ├── postback ────► c ไม่ตรงแคมเปญที่เปิดอยู่ → ERR-100
  │                  d ไม่ตรงวันนี้           → ERR-103
  │                  ผ่าน                     → เล่นกิจกรรม (§6)
  ├── message ─────► pending_input → keyword_rule → channel.default_card_id
  └── follow ──────► greeting_enabled ?
                       ├── true  → activity ที่ trigger='follow' ถ้ามี
                       │            ไม่มี → channel.greeting_card_id
                       └── false → ไม่ตอบ ปล่อยให้ OA Manager ทักทายเอง
```

**ห้ามมีทางไหนจบแบบเงียบ** (BR-01) — ทุกกิ่งมีการ์ดตอบของตัวเอง

### 5.2 กิ่งสลับแท็บต้องมาก่อน

`params.status` ไม่มี `c=` `a=` `d=` แนบมา ถ้าไม่แยกออกก่อน มันจะร่วงไปถึงกิ่งสุดท้าย
แล้วตอบว่า "กิจกรรมนี้จบไปแล้ว" — **กลายเป็นแตะแท็บทีนึงได้ข้อความรบกวนทีนึง**

ค่าที่ LINE ส่งกลับมา: `SUCCESS` · `RICHMENU_ALIAS_ID_NOTFOUND` · `RICHMENU_NOTFOUND` · `FAILED`
ไม่ใช่ `SUCCESS` → บันทึกและแจ้งคนดูแล (ERR-042) · **ยังไม่ตอบข้อความหาผู้ใช้อยู่ดี**

สไลซ์นี้ยังไม่มีริชเมนู แต่**กิ่งนี้ต้องมีตั้งแต่แรก** เพราะถ้า P2 มาเพิ่มทีหลังแล้วลืม
จะเป็นบั๊กที่ผู้ใช้เจอก่อนเรา

### 5.3 config อ่านครั้งเดียว แคชตลอดไป

`config_version` แก้ไม่ได้ตลอดกาล (BR-05) → แคชได้โดยไม่ต้องมีกลไกล้างแคชเลย

```
key = config_version.id      ค่าไม่เคยเปลี่ยน → ไม่มีวันเก่า
publish ใหม่ = version ใหม่ = key ใหม่ → ไม่ต้อง invalidate อะไรสักอย่าง
```

ข้อนี้ตกมาจากกฎที่เอกสารเขียนไว้เพื่อเหตุผลอื่นทั้งหมด (ตรวจย้อนหลังได้) แล้วได้ความเร็วมาฟรี

### 5.4 งบเวลา

| ขั้น | เวลา |
|---|---|
| ตรวจลายเซ็น | ~0 |
| โหลด config | ~0 (แคช) |
| อ่านสถานะผู้เล่น + โควตา | 1 รอบ |
| `decide()` | ~0 (pure) |
| RPC เขียน | 1 รอบ |
| render | ~0 (pure) |
| **Reply API** | **เหลือเวลาเกือบทั้งก้อนให้ตัวนี้** |

เป้า P95 < 1.5 วินาทีจึงขึ้นกับเน็ตไป LINE เกือบทั้งหมด ซึ่งเป็นสิ่งที่ควรเป็น —
ถ้างบหมดไปกับฐานข้อมูล แปลว่าออกแบบผิด

> **1.5 วินาทีเป็นค่าเผื่อ ไม่ใช่ค่าจริง** — OI-03 ยังไม่วัด · `event_log.duration_ms`
> ต้องมีตั้งแต่ deploy ครั้งแรกเพราะเก็บย้อนหลังไม่ได้

## 6. เส้นแบ่งธุรกรรม

### 6.1 ตัดสินก่อน แล้วปิดงานในรอบเดียว

```
1  อ่าน config (แคช) + สถานะผู้เล่น + โควตาคงเหลือ
2  decide() ใน TS → ผลลัพธ์ที่ "เรียงตามลำดับความชอบ"
3  RPC เดียว atomic:
      จอง play_lock (participant, activity, period_key)
      ├── ชนกับแถวเดิม → คืน result ที่เก็บไว้ · ไม่ตัดสินใหม่ ไม่แจกซ้ำ   BR-32
      └── จองได้
            ไล่รายการที่ส่งมา หยิบตัวแรกที่โควตายังเหลือจริง → ตัดโควตา
            เขียน entitlement · counter_value · effect_log · play_lock.result
            คืนว่าหยิบตัวไหน หรือ null ถ้าหมดทุกตัว
4  null → ใช้ fallback_card_id (BR-31 บังคับให้มีอยู่แล้ว)
5  render (pure) → Reply API → INSERT event_log พร้อม duration_ms
```

### 6.2 ทำไมแบ่งเส้นตรงนี้

**SQL ไม่มีตรรกะธุรกิจเลย** มันแค่ "หยิบตัวแรกที่ยังเหลือ" ซึ่งเป็นงานที่ต้องกันการแข่งกัน
ส่วนการตัดสินว่าเรียงลำดับยังไงอยู่ใน TS ทั้งหมด — ล็อก seed เทสต์ได้ และวัด AC-01 ได้

**สามอย่างต้องอยู่ในธุรกรรมเดียวกัน** — จอง lock · ตัดโควตา · เขียนผล
ถ้าแยกแล้วล้มระหว่างกลาง จะได้ lock ที่ไม่มีผล → คนกดซ้ำได้การ์ดเปล่า
และกดใหม่ไม่ได้ตลอดวันเพราะ lock ยังอยู่

**เคสที่โควตาหมดระหว่างอ่านกับเขียน** คือเคสที่ BR-31 บังคับให้มีการ์ดสำรองไว้เพื่อสิ่งนี้ตรงๆ
ไม่ต้องวนใหม่ ไม่ต้อง retry

**สิ่งที่อยู่นอกธุรกรรมโดยตั้งใจ** — `event_log` เขียนหลังตอบ เพราะ `duration_ms` วัดได้
หลังตอบเท่านั้น · ถ้าเขียนไม่สำเร็จ ผู้ใช้ก็ได้คำตอบไปแล้ว ซึ่งเป็นลำดับความสำคัญที่ถูก

### 6.3 ผลข้างเคียงทางเทคนิค

`supabase-js` คุยผ่าน REST จึงสั่ง `BEGIN`/`COMMIT` ไม่ได้ → ต้องมี SQL function เป็น RPC
อยู่แล้วไม่ว่าจะเลือกทางไหน · ทางนี้แค่ใช้มันให้คุ้มด้วยการยุบเป็นรอบเดียว

### 6.4 จังหวะ milestone

ตรวจจุดปลดล็อก **ทันทีในรอบเดียวกับการตอบ ไม่ใช่เข้าคิว** — อยู่ใน RPC เดียวกัน
ผู้ใช้ที่สะสมถึงจุดต้องเห็นผลในการ์ดใบเดียวกันกับที่ทำให้ถึง

## 7. การ์ดกับ renderer

### 7.1 บล็อกในสไลซ์นี้ · 8 จาก 10 ชนิด

| ชนิด | สถานะ |
|---|---|
| ภาพ · หัวข้อ · ข้อความ · ปุ่ม · **แถบความคืบหน้า** | ต้องออกแบบ UI |
| ข้อความรอง · เส้นคั่น · ช่องว่าง | ได้ฟรี — ใช้โครงเดียวกัน หรือไม่มีค่าให้กรอก |
| แถวสถานะ · ช่องแสตมป์ | เลื่อน — ต้องต่อกับ `stamp_card` |

**แถบความคืบหน้าคือตัวที่ LINE ทำไม่ได้** และเป็นเหตุผลที่มันอยู่ในชุดแรก —
ถ้าสไลซ์แรกไม่มีอะไรที่ LINE ทำไม่ได้เลย เราก็ยังไม่ได้พิสูจน์อะไร

### 7.2 ผลลัพธ์กลางสามกลุ่ม

```
card_block[] + PlayerState
        │
        ▼  groups.ts   ← ที่เดียวที่ตัดสินว่าบล็อกไหนไปกลุ่มไหน
   { top, content, footer }
        │
   ┌────┼────────┬──────────────────┐
   ▼    ▼        ▼                  ▼
flex.ts text.ts  preview (HTML)  image (P3 · OI-27)
```

กฎการจัดกลุ่ม — **ต้องรักษาลำดับ** (BR-92)

```
top     = ภาพที่เป็นบล็อกแรก ถ้าตั้งเป็นเต็มความกว้าง
footer  = ปุ่มที่ต่อกันเป็นพืดอยู่ท้ายรายการ
content = ที่เหลือทั้งหมด ตามลำดับเดิม
```

**ปุ่มที่อยู่กลางรายการต้องอยู่กลาง ไม่ถูกดันลงท้าย**

### 7.3 สถานะของผู้เล่นเป็นก้อนเดียว

```ts
type PlayerState = {
  attributes:   Record<string, string>
  counters:     Record<string, number>
  entitlements: string[]
  lastResult?:  string
}
```

ก้อนนี้เป็นทั้งอินพุตของตัวแปร `{{counter.food}}` และของ `show_when` จึงเป็นก้อนเดียวกับ
ที่สวิตช์สลับสถานะในหน้าตัวอย่างเปลี่ยน (BR-83) · แยกเป็นสองก้อนแล้วตัวอย่างจะโกหกได้

### 7.4 หน้าตัวอย่างไม่ใช่ความจริง — และต้องไม่แกล้งว่าเป็น

`preview (HTML)` คือ CSS ที่เราเขียนเลียน LINE ไม่ใช่ LINE จริง · เป็นความเสี่ยงตระกูล
เดียวกับ BR-88 และเลี่ยงไม่ได้เพราะ LINE ไม่มี renderer ให้ฝัง

| ทาง | ใช้ทำอะไร |
|---|---|
| หน้าตัวอย่าง | ดูโครงกับเงื่อนไข — เร็ว ไม่ต้องต่อเน็ต |
| ปุ่มดู Flex JSON | ก๊อปไปวางใน Flex Message Simulator ของ LINE |
| **ปุ่มส่งทดสอบเข้า LINE ตัวเอง** | **ความจริงมีอยู่ทางนี้ทางเดียว** |

ปุ่มส่งทดสอบต้องอยู่ในสไลซ์แรก ไม่ใช่ของเสริม — ไม่งั้นเราจะเชื่อ CSS ตัวเองไปสองเดือน

### 7.5 หน้าตั้งค่าการ์ด · M3-S02

```
ขั้น 1  เลือกชนิดการส่ง     การ์ดเดี่ยว · การ์ดปัดได้ · ข้อความล้วน     BR-89
ขั้น 2  เลือกเทมเพลต        รวม "เริ่มจากศูนย์" อยู่ในชุดเดียวกัน       BR-63
ขั้น 3  แก้บล็อก
```

ทุกบล็อกมีสามส่วนเหมือนกันหมด — **ค่าของตัวเอง · สวิตช์ตามสถานะ · เงื่อนไขการแสดง**

**ปุ่มพิเศษกว่าบล็อกอื่น** — ป้ายเปลี่ยนตามสถานะได้ผ่าน `selector_id` แต่ปลายทางใน
`options` ต้องคงที่เสมอ (BR-40) · หน้าจอต้องขึ้นกุญแจให้เห็น ไม่ใช่ซ่อนตัวเลือกไปเฉยๆ

ตัวนับต้องเห็นตลอด — **บล็อก 10 · ปุ่ม 3** (BR-66)

## 9. การจัดการข้อผิดพลาด

### 9.1 ข้อความสำรองห้าข้อฝังในโค้ด ไม่ใช่ใน config

เพราะใช้ตอนที่ config เชื่อถือไม่ได้แล้ว

| รหัส | เกิดเมื่อ | ระบบทำอะไร |
|---|---|---|
| ERR-100 | postback อ้างแคมเปญที่ไม่ได้ publish อยู่ | "กิจกรรมนี้จบไปแล้ว ขอบคุณที่ร่วมสนุก" |
| ERR-101 | ปุ่มควิซของรอบเก่า | การ์ดของ config ถ้ามี · ไม่มีใช้ "ชุดคำถามนี้จบไปแล้ว" |
| ERR-102 | รางวัลหมดทุกแบบและไม่มีการ์ดสำรอง | **ไม่ควรเกิด** เพราะ BR-31 บังคับกรอก · เกิดแล้วแจ้งทีมทันที |
| ERR-103 | การ์ดเก่าที่ date key ไม่ตรงวันนี้ | การ์ดของ config ถ้ามี · ไม่มีใช้ "การ์ดนี้หมดอายุแล้ว" |
| ERR-104 | engine หรือ renderer ล้มเหลว | "ระบบขัดข้องชั่วคราว กรุณาลองใหม่" · **ต้องตอบเสมอ** (BR-01) |

### 9.2 บทเรียนสามข้อจากโค้ดเดิมที่ยกมาใช้ต่อ

มาจาก commit `9b51ed6` ที่แก้ปัญหาจริงบน LINE

1. **ตอบ 200 ให้ LINE ก่อนประมวลผล** — LINE ไม่สนใจผลของเรา และ retry จะทำให้แจกซ้ำ
2. **กันแชทกลุ่มไม่ให้ถูกสแปม** — event จากกลุ่มมี `source.type = 'group'`
3. **ใส่ timeout ให้ทุกการเรียก LINE** — ค้างจน reply token หมดอายุคือความเงียบที่ผิด BR-01

## 10. เทสต์

### 10.1 สามชั้น

| ชั้น | ทดสอบอะไร | ต้องมี DB |
|---|---|---|
| unit | engine · render · match · daykey · verify | ❌ |
| integration | ธุรกรรม atomic · โควตา · schema ตรงเอกสาร | ✅ local Postgres |
| regression | snapshot ของ Flex JSON | ❌ |

**ชั้น unit ต้องรันได้โดยไม่ต่อเน็ตและไม่มีฐานข้อมูล** — เป็นข้อบังคับ ไม่ใช่ความสะดวก
เพราะเป็นชั้นที่จะถูกรันทุกครั้งที่แก้โค้ด

### 10.2 รายการที่ต้องมี

**unit**

- ทุกกิ่งขาเข้าคืนคำตอบ · ไม่มีกิ่งไหนคืน `null`
- ลายเซ็นผิด → 401 · ถูก → 200
- สลับแท็บ 10 ครั้ง → Reply API ไม่ถูกเรียกเลย
- ปุ่มกลางรายการไม่ถูกดันลงท้าย (BR-92)
- `show_when` ไม่ผ่าน → บล็อกหายจากทั้งสามกลุ่ม
- ตัวแปรที่ไม่มีค่า → ไม่โผล่ `{{...}}` ให้ผู้ใช้เห็น
- ปลายทางปุ่มผูก `selector` ไม่ได้ (BR-40)
- `resolve` แบบ `weighted` ล็อก seed แล้วได้ผลเดิมทุกครั้ง
- `daykey` ข้ามเที่ยงคืนตาม `day_length` ที่ตั้งไว้ ไม่ใช่ตามเที่ยงคืนจริง
- postback ยาวเกิน 300 ตัวอักษร → ปฏิเสธตอนสร้าง ไม่ใช่ตอนส่ง

**integration**

- กดซ้ำ 5 ครั้ง → ผลเดียวกัน แจกรางวัลครั้งเดียว
- **ยิง 50 คำขอพร้อมกันบนรางวัลโควตา 10 → ออกพอดี 10 ใบ**
- `content` + `selector_id` พร้อมกัน → DB ปฏิเสธ
- สอง `is_entry = true` ในแคมเปญเดียว → DB ปฏิเสธ
- สอง `trigger = 'follow'` ในแคมเปญเดียว → DB ปฏิเสธ
- สคริปต์เทียบ schema กับเอกสารผ่าน

**regression**

```
tests/__snapshots__/flex/*.json     ← JSON ที่ส่งเข้า LINE จริง
```

ครอบการ์ดชุดตัวอย่างทุกใบ × ทุกสถานะที่ `show_when` แยกทาง

แก้ renderer แล้วรูปร่างข้อความเปลี่ยนโดยไม่ได้ตั้งใจ **เทสต์ฟ้องเป็น diff ทีละบรรทัด**
และเวลาเปลี่ยนโดยตั้งใจก็ต้องกด approve ใหม่ ซึ่งกลายเป็นบันทึกว่ารูปร่างข้อความ
เปลี่ยนตอนไหนเพราะอะไร

### 10.3 เทสต์ที่สำคัญที่สุดสองตัว

1. **ยิงพร้อมกัน 50 บนโควตา 10** — ตัวเดียวที่พิสูจน์ว่ากันการแข่งกันได้จริง
   และเป็นบั๊กที่ถ้าไม่มีเทสต์จะไม่มีใครเจอจนกว่าจะมีคนเล่นเยอะ
2. **เทสต์ไล่ import ของ `engine/` และ `render/`** — ตัวเดียวที่กันสถาปัตยกรรมไม่ให้ละลาย

### สามข้อที่ต้องตัดสินก่อนเขียนตาราง ไม่ใช่ก่อนเขียนหน้าจอ

แม้หน้าจอทั้งสามจะอยู่นอกสไลซ์นี้ แต่ **ถ้าตารางออกแบบผิดตั้งแต่ migration แรก
จะกลับไปแก้ไม่ได้**

| จอ | ถ้าไม่ตัดสินตอนนี้ |
|---|---|
| M11-S01 API key | เก็บกุญแจแบบอ่านกลับได้แล้ว จะทำ "แสดงครั้งเดียว" ไม่ได้อีก |
| M10-S02 ส่งออกข้อมูล | ไม่มีช่องเหตุผลใน `export_log` ตั้งแต่แรก ไฟล์เก่าจะไม่มีเหตุผลติดมา |

**ข้อเสนอ** — ทั้งสามตารางอยู่ในกลุ่มที่สร้างครบตั้งแต่ migration แรกอยู่แล้ว
ให้ใส่ช่องที่จำเป็นไว้เลย (เก็บกุญแจเป็น hash · `export_log.reason` · `token_access_log`)
แม้หน้าจอจะยังไม่มี · **ต้นทุนตอนนี้คือสามคอลัมน์ ต้นทุนตอนหลังคือ migration บนข้อมูลจริง**
