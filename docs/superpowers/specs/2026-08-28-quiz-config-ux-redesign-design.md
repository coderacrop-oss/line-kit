## 3. Mental model (ตาม pattern ของ reference)

Setup mode เป็นหน้าเดียวที่ scroll ผ่าน 3 ขั้นตอนเรียงเลข — ไม่ใช่ tab:

1. **แกน (Axes)** — เท่ากับของเดิม แต่แสดงเป็น chip ที่ยุบ/ขยายได้ (คลิกเพื่อแก้ id/label/ขั้ว)
2. **คำถาม (Questions)** — คะแนนของแต่ละตัวเลือกต่อแต่ละแกนเป็น **score dial** (ปุ่มคลิกทีละระดับ -5..+5
   ไม่ใช่ number input) — 11 ระดับ เพราะ schema ของจริง (`QuizOption.scores` ค่าเดี่ยว) บังคับ `-5..5` (ต่างจาก
   ตัวอย่างในสเปกที่ใช้ช่วงแคบกว่า — ใช้ขอบเขตจริงของ repo นี้ตามที่โจทย์สั่ง)
3. **ผลลัพธ์ (Results)** — คลิกช่องในกริด/checklist เพื่อแก้/สร้างผลลัพธ์นั้น แทนลิสต์ยาว

Sidebar ซ้าย (fixed/sticky) แสดงภาพรวมตลอดเวลา: จำนวนแกน/คำถาม/ผลลัพธ์ + เมทริกซ์ย่อ (✅/⚠️) +
สถานะ validate (พร้อมใช้ / ขาด N อย่าง) — คำนวณจาก `draft` state เดิมที่มีอยู่แล้ว ไม่มี "ปุ่มตรวจสอบ" แยก

โหมดบนสุด `[📐 ตั้งค่า] [▶ ลองเล่น]` คุมว่าเห็น Setup หรือ Play

## 4. จุดที่ shape ข้อมูลจริงไม่ตรงกับ pattern ต้นแบบเป๊ะๆ — และวิธีแก้

### 4.1 กริดผลลัพธ์โหมด solo ไม่มี "คู่แกน" ให้จับคู่

Duo จับคู่ผลลัพธ์ด้วย `results[].pair: [axisId, axisId]` (เทียบแบบไม่สนลำดับใน `matchPair()`) — เป็นกริด
N×N ตามแกนได้ตรงๆ

Solo **ไม่มี pair เลย** — `resolveSolo()` คำนวณ `typeCode` จาก `dominantAxis()`: เอา **ตัวอักษรตัวแรกของขั้วที่
คะแนนเอียงไป** ของทุกแกน มาต่อกันตามลำดับที่ประกาศแกนไว้ (เช่น 2 แกน E/I กับ S/N → typeCode มีได้ 4 แบบ:
`ES ES` ไม่ใช่ ผสมจริงคือ `EI×SN` cartesian = 4 รหัส) แล้วเทียบกับ `results[].code` (case-insensitive ตรงตัว
เป๊ะ ไม่มี catch-all สำหรับ solo — ไม่ตรงเป๊ะ = ไปที่ `fallbackResultCode` เงียบๆ เสมอ)

**วิธีแก้ที่ใช้**: คำนวณ "รหัสที่เป็นไปได้ทั้งหมด" ล่วงหน้าเป็น cartesian product ของอักษรตัวแรกของขั้วซ้าย/ขวา
ต่อแกน (สูงสุด 2^6 = 64 เมื่อมี 6 แกน แต่ในทางปฏิบัติแคมเปญจริงมักมี 2-3 แกน = 4-8 รหัส) แล้วแสดงเป็น
checklist ของ "รหัสที่ควรมี" พร้อม ✅ (มี result ตรงรหัสนี้จริง) / ⚠️ (ยังไม่มี — ตอนนี้ตกไป fallback) ตรงตาม
คำแนะนำของโจทย์ข้อที่บอกให้ "ใช้ list ของรหัสที่คาดหวัง พร้อม ✅/⚠️ แทนกริดตรงๆ" คลิกช่องที่ ⚠️ จะสร้างผลลัพธ์
ใหม่พร้อม `code` เติมไว้ให้แล้วเปิดตัวแก้ไข

### 4.2 Catch-all (ผลลัพธ์ไม่มี `.pair`) ในโหมด duo ไม่ใช่ "ขาด" จริงๆ

ผลลัพธ์ duo ที่ไม่ระบุ `.pair` จะจับคู่ **ทุกคู่ที่ยังไม่ตรงกับ rule ก่อนหน้า** (`matchPair()` วนจากบนลงล่าง คืน
ทันทีที่เจอ rule ไม่มี `.pair`) เมทริกซ์จึงต้องแยก 3 สถานะ ไม่ใช่ 2: ตรงเป๊ะ (explicit) / ถูกคลุมด้วย catch-all
(กันไว้แล้วแต่คนละแถว) / ไม่มีอะไรคลุมเลย (missing จริง) — ใช้สีต่างกัน (ok vs info vs warn จาก `STATUS_TONES`)
ไม่ใช่ ✅/⚠️ สองสถานะเฉยๆ เพราะ "มี catch-all คลุมอยู่" กับ "missing แล้วจะไปตก fallback" มีความหมายต่างกันคนละ
เรื่องกับผู้ใช้

### 4.3 "ตั้งค่าเพิ่มเติม" ของ repo นี้ไม่ใช่ brand/copy — เป็น group config

Reference บอกให้ซ่อน "brand/copy/rules/messages" ไว้หลัง `⚙️ ตั้งค่าเพิ่มเติม` — แต่ระบบนี้ **แยก
brand/copy (`templateCopy`) ไปอยู่จอ M14-S01 (`template/page.tsx`) และการ์ดแจ้งเตือนไปอยู่จอ M7-S06
(`replies/page.tsx`) อยู่แล้ว ตั้งแต่ก่อนงานนี้** — ทั้งสองมีลิงก์อยู่ที่หัวจอ M7-S05 (`Replies →`, `เทมเพลต →`)
สิ่งเดียวที่ยัง "แทรก" อยู่ใน `QuizConfigForm.tsx` ที่ไม่ใช่แกน/คำถาม/ผลลัพธ์หลักคือ **`GroupConfigEditor`**
(ตั้งค่าโหมดกลุ่ม — ใช้เฉพาะ duo, ส่วนใหญ่ปิดอยู่) ตัวนี้จึงเป็นสิ่งที่ถูกซ่อนหลัง `⚙️ ตั้งค่าเพิ่มเติม` แทน
ไม่ได้ผิดเจตนาเดิม เพราะมันคือ "ของที่แก้ไม่บ่อย" ตัวเดียวที่เหลืออยู่ในจอนี้จริงๆ

### 4.4 หน้า Replies มี "flow" เดียว ไม่ใช่ 6 จุดแบบ KimLIFF

สเปกอ้างอิงบอกให้ทำ accordion หลาย flow (Reply/Push/ShareTargetPicker) แต่ `QuizReplies` ใน repo นี้
(`lib/quiz/schema.ts`) มีฟิลด์เดียวคือ `duoMatchNotifyCardId` — และสเปกที่สร้างฟีเจอร์นี้ไว้ก่อนหน้า
(`docs/superpowers/specs/2026-08-25-quiz-duo-reply-notify-design.md` §2) **เขียนไว้ตรงๆ ว่า** "ทำแค่จุดเดียว
ก่อน หน้า `.../quiz/replies` ตอนนี้จึงมีแค่ฟิลด์เดียว ไม่ใช่ console เต็มรูปแบบ" — จุดสัมผัสอื่นๆ ที่มีข้อความจริง
(`duoInvite`/`duoPairResult`/`groupComplete`/ฯลฯ) อยู่ใน `templateCopy.messages` ของจอ M14-S01 คนละจอ

**วิธีแก้**: สร้าง `FlowCard` แบบ generic (เลขลำดับ, ชื่อ, pill สี, trigger box, ฟิลด์ซ้าย, พรีวิวขวา) ให้พร้อม
ขยายในอนาคต แต่ **ใส่ instance เดียว** สำหรับข้อมูลจริงตอนนี้ (`duoMatchNotify`, เปิดเฉพาะโหมด duo, pill "Push
· นับ quota" สีเหลือง เพราะ `lib/db/quizNotify.ts` ยิงผ่าน `pushMessage()` ของ LINE จริง ไม่ใช่ reply
webhook ฟรี) แถบสรุปบนสุดจึงเป็น "จุดที่ส่งข้อความ: 1 · ฟรี: 0 · Push: 1" (duo) หรือ "0 · 0 · 0" (solo — ยังไม่มี
จุดไหนให้ตั้งเลย ตรงกับที่สเปกบอกว่า solo มี flow น้อยกว่า duo ในกรณีนี้คือน้อยกว่าจนเป็นศูนย์)

ฟิลด์ที่แก้ได้จริงในจอนี้มีแค่ "เลือกการ์ดที่จะส่ง" (dropdown) ไม่มีข้อความให้พิมพ์ตรงนี้เลย (เนื้อหาการ์ดแก้ที่
จอการ์ดของมันเอง) พรีวิวขวาจึงไม่ใช่ live-typed text เหมือนสเปกอธิบาย — เป็น **พรีวิวของการ์ดที่เลือกอยู่** แทน
(ชื่อ/ชนิด/มีภาพไหม/ตัวอย่างข้อความหัวการ์ด) โดยดึงจาก `CardView` ที่ `listCardsForActivity()`/`summarizeCard()`
คำนวณไว้แล้ว (ไม่ query ใหม่ ไม่เพิ่ม field ใน schema) พร้อมลิงก์ "แก้ไขการ์ดนี้ →" ไปหน้าการ์ดจริงเพื่อแก้เนื้อหา

## 5. ที่ไม่ทำในสไลซ์นี้ (บอกตรงๆ ไม่ใช่ตกหล่นเงียบๆ)

- **ลองเล่น (Play mode)** — โหมดที่สองของสวิตช์บนสุดจะขึ้น แต่เนื้อหาข้างในเป็น placeholder อธิบายว่าจะมี
  phone simulator + คะแนนสดเมื่อไหร่ทำ ไม่ใช่ตัวจำลองจริง — การสร้าง renderer แชท LINE + ตัวเล่นคำถามจริง
  เป็นงานอีกก้อนใหญ่แยกต่างหาก (ต้องมี state ของคำตอบทีละข้อ, เรียก `resolveSolo`/`resolvePair` จริง,
  render ตามธีมแคมเปญ) นอกขอบเขตของสไลซ์นี้ที่โฟกัสที่ตัว config UI
- **ปุ่ม Export ซ้ำในแถบข้าง** — ของเดิมมีอยู่แล้วที่หัวจอ (`ExportButton`) ไม่ทำซ้ำในแถบข้างเพื่อไม่ให้มีสอง
  ทางเข้าที่ต้องคอยให้ตรงกัน (ต้องส่ง `activityName` เพิ่มเป็น prop ใหม่ทั้งที่ของเดิมพอแล้ว)
- **แก้เนื้อหาข้างใน `GroupConfigEditor.tsx`** — ตัวฟอร์มข้างในทำงานถูกอยู่แล้วและมีเทสต์คุ้มครองครบ
  (`GroupConfigEditor.test.tsx`) เปลี่ยนแค่ที่ห่อจากภายนอก
